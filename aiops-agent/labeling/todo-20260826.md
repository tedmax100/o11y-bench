## 怎麼標

Grafana → Apps → AIOps → **Todo**，或用 CLI：

```bash
kubectl -n demo exec deploy/aiops-agent -- python -m app.calibration label <fp> --correct   # 或 --wrong
```

`grading_mode` 兩種：**culprit**（兇手指對了嗎，校準門只讀這種）、**inconclusive**（沒事的時候有沒有適當保留）。
把 inconclusive 標成 culprit 就是 Day29 那個 MCE 1.0 的坑。

## 刻意不標的兩筆

### `fb490a75-…`「一切正常」conf 0.9

要判它得有 2026-08-17 那天的資料，早就過保留期了。而且**同一段對話 22 分鐘前
（16:22:02，conf 0.4）才說「api-gateway 有大量 5xx」**，接著兩次自己收回成
inconclusive。在這種來回之後，「一切正常」是對是錯我沒有證據說得準。
沒證據就標，正是校準池上次被污染的原因。

### `a93580b3-…`「各服務請求速率」conf 1.0

它報 api-gateway 跟 webapp 都是 **≈4.75 req/s**。4.75 是這套 demo 上已知的假數字
——`*_duration_seconds` 記秒進毫秒桶造成 `histogram_quantile` 恆為 ~4.75 的那個
artifact。兩個不同服務報同一個 4.75，比較像是那個 artifact，不像是流量。
再加上 demo 的 metrics 沒有 pod/instance label、多 replica 會疊成一條 series，
這個數字本來就不可信。**這筆該做的不是標對錯，是去查那個 4.75 從哪來的。**

**（當天稍晚查完了）** 叢集上**六個服務的 p95 全部都是 4.75**，一模一樣。
`http_server_duration_milliseconds` 是自動儀器化打的，用 SDK 預設桶 `[0,5,10,…]`，
而這裡所有請求都在 5ms 以內 → 全落進第一個桶 → `histogram_quantile` 永遠內插出 4.75。
同一時間真實的請求速率是每個服務都不同的（0.27–0.53 req/s 這個量級）。
所以那筆是把一個延遲的假數字當成流量報出來，conf 1.0。
**維持不標**：它確實答錯了，但錯在數字，而 culprit／inconclusive 兩把尺量的是
「兇手指對了嗎」與「該不該指認」，都量不到「報的數字對不對」。

## 順手修掉的兩個 bug

1. **Todo 清單裡的 chat run 根本標不了**：chat 只寫 `investigations`、不寫
   `calibration`，`label_run` 一律 404。佇列裡有做不了的事，人就不會再看佇列了。
   → `_backfill_from_investigation()`：沒有列就從 investigation 補一列 pending 的。
2. **唯一的標註入口寫死 culprit**：`POST /investigations/{fp}/label` 不管 run 有沒有
   指認過任何人，一律寫 culprit。→ 新增 `default_grading_mode()`，**從 run 自己判**
   （沒指認任何人 → inconclusive），API 也可以明寫 `grading_mode`；CLI 補上
   `--grading-mode / --dimension / --note`。
