### 🕒 第 5 小時：企業級應用 — 整合遺留系統與共享生態

#### 🏢 第一階段：Comcast 經驗分享 — 遺留系統的共存策略 (25 分鐘)

**【教學目標】學習大型企業如何透過架構設計，讓舊有系統與 OTel 標準無縫接軌。**

* **Comcast 的真實挑戰：**
  講師分享業界巨頭 Comcast 的案例。Comcast 在遷移其超過 3,000 個微服務時面臨了巨大的挑戰。雖然部分團隊可以順利採用 OpenTelemetry 函式庫與標準語義慣例，但有許多遺留應用程式（Legacy applications）仍有其獨特的屬性需求，用以維持現有的視覺化或警報系統。如果強迫所有系統立刻改寫，將會產生極大的遷移阻力。
* **靈活的屬性注入 (Attribute Injection)：**
  為了讓新舊系統並存，Comcast 團隊採取了一項聰明的做法。他們將 OpenTelemetry 的標準語義慣例庫下載到本地，然後 **直接將代表公司內部專用屬性的命名空間（Namespace）以資料夾的形式「注入」到標準的目錄結構中** 。
* **打造單一的 Schema 真實來源 (Single Source of Truth)：**
  當他們執行 Weaver 指令時，Weaver 會同時讀取 OTel 標準與 Comcast 客製化的屬性。搭配 Jinja 樣板，他們甚至能過濾掉已廢棄（deprecated）的屬性、將型別對應到目標系統（如 Elasticsearch 支援的型別），最終產出一份單一的 JSON Schema 結構檔。
  **核心價值：** 這為所有開發團隊提供了一個單一的追蹤屬性來源（Single source for trace attributes）。不同團隊能依照自己的步調遷移，且不需要中斷遺留應用程式的運行，大幅降低了推行標準化的摩擦力。

#### 🌐 第二階段：發布與共享企業專屬的註冊表 (15 分鐘)

**【教學目標】探討企業如何將內部規範封裝並發布，供生態系中的其他團隊與平台使用。**

* **定義企業的專屬生態圈：**
  Weaver 鼓勵企業建立自己的語義慣例註冊表，並在有需要時重複利用 OTel 的官方標準。例如，F5 Network 未來可能會為 NGINX 建立一份專屬的遙測物件目錄，並透過 Weaver 將其發布出來。
* **供下游系統自動調用：**
  你不僅是在規範自己的應用程式碼，Weaver 允許開發者將本地專案定義的 Metric、Span 或 Event 發布為開放格式。這樣一來，不論是公司內部的其他開發團隊，還是下游的資料庫引擎與監控平台，都能直接調用並解析這份「客製化語義慣例」，確保上下游對於遙測欄位的認知完全一致。

#### 🚀 第三階段：未來展望 — 動態適應與資料目錄整合 (15 分鐘)

**【教學目標】探索 Weaver 在未來遙測架構演進中的前瞻性應用與社群發展路線。**

* **查詢時的動態適應 (Dynamic Query Adaptation)：**
  當指標名稱發生變更時，以往 SRE 需要手動修改大量的警報與查詢語法。目前 Weaver 團隊正與 Prometheus 社群合作探索一項革命性的機制：未來我們可以透過發布指標變更的差異檔案（利用 `weaver registry diff` 功能），讓 **下游資料庫在查詢時能夠「動態適應 (dynamically adapt at query time)」這些指標變更** 。這意味著資料庫會自動讓查詢語法兼容新舊兩個版本的指標，實現警報與儀表板的無痛轉移。
* **原生整合資料目錄 (Data Catalogs)：**
  Weaver 未來的發展路線圖中，包含了將註冊表與「資料目錄 (Data catalogs)」及各大可觀測性工具進行原生整合的計畫。
* **WASM 外掛擴充生態系：**
  未來的 Weaver 架構將引入更豐富的生態系統，例如透過整合 WASM 外掛程式，進一步支援資料目錄建置、隱私合規驗證以及儀表板生成等進階應用。這將使 Weaver 從單純的 CLI 工具，徹底轉化為企業級遙測治理的中樞神經。
