### 🕒 第一小時：觀念啟蒙 — 可觀測性即設計 (Observability by Design)

#### 📝 開場與痛點分析 (10 分鐘)

**【教學目標】喚起學員共鳴，點出目前業界在遙測數據管理上的混亂現況。**

* **情境提問：** 講師可以先詢問台下學員是否經歷過以下幾種令人崩潰的情況：
  1. **警報失效：** 部署了新的更新後，所有的警報和儀表板突然壞掉，因為某個工程師不小心更改了指標 (Metric) 的名稱。
  2. **查詢語法變得極度複雜：** 因為不同團隊的命名不一致（例如：A 團隊用 `host-name`，B 團隊用 `host_name`），導致你在寫查詢時，必須使用一堆 `OR` 條件才能把資料撈齊。
  3. **缺乏文件與能見度：** 團隊成員在設定警報時，根本不知道有哪些指標可以拿來用，或是這些遙測訊號含糊不清且沒有文件說明。
  4. **生產環境盲區：** 系統出了大問題，到了生產環境 (Production) 排查時，才發現根本 **缺少了關鍵的監控數據 (Missing instrumentation)** 。
* **追蹤的跨團隊挑戰：** 在一個微服務架構中（例如：前端呼叫認證層，再呼叫庫存層），追蹤 (Tracing) 天生就會跨越不同的團隊領域。如果大家對於「客戶 ID」的屬性命名沒有共識（有的叫 `client_id`，有的叫 `clientId`），當我們需要在後端追蹤平台上查詢特定客戶的歷程時，這項工作將變得極度脆弱且耗費人力。

#### 🧠 核心理念引入：可觀測性即設計 (20 分鐘)

**【教學目標】介紹全新思維，將遙測指標的地位提升至與程式碼同等重要。**

* **什麼是「可觀測性即設計 (Observability by Design)」？**
  * 就像業界常說的「Security by Design（安全即設計）」或「Privacy by Design（隱私即設計）」一樣，這是一種 **將可觀測性工作流直接整合進軟體開發生命週期 (SDLC) 的全新概念** 。
  * **核心定義：** 我們必須 **將遙測訊號（包含指標、追蹤、日誌）視為系統的一等「公開 API」** 。這意味著遙測資料需要具備與應用程式碼完全相同的品質標準。
* **如何實踐？**
  * **明確目標：** 從開發人員、SRE 到產品經理，必須共同定義出營運該產品最關鍵的訊號。
  * **自動化流程：** 改變過去只有單元測試的習慣，我們需要引入一套自動化機制來：自動生成遙測文件、保持文件與規格同步、為系統客製化生成專屬的強型別 (Type-safe) 客戶端 SDK，並在程式碼修改時比對差異，確保其相容性。

#### 🏛️ 基礎建設：語義慣例 (Semantic Conventions) (15 分鐘)

**【教學目標】說明 OpenTelemetry 如何透過標準化解決命名混亂的問題。**

* **統一的溝通語言：** 語義慣例 (Semantic Conventions) 是一套共通的命名架構，可以用來標準化程式碼庫、函式庫與平台之間的名稱，從而讓資料的關聯與消費變得更加容易。它本身就是一個屬性與規範的「型錄 (Catalog)」。
* **「T 型 (T-shaped)」定義策略：** OpenTelemetry 的語義慣例採用了 T 型定義。
  * **廣度 (Broad)：** 提供一套廣泛且簡單的標準，例如「應該如何監控所有的 HTTP 伺服器」。
  * **深度 (Deep)：** 針對特定領域提供深度的指標定義，例如「如何監控 Go 語言的 Runtime (執行環境)」。
* **Schema URL：** 在程式庫中標示支援的 Schema URL，可以讓應用程式中不同的儀表板或追蹤工具清楚知道目前遵循的確切版本。

#### 🛠️ 破局工具：OpenTelemetry Weaver 簡介 (15 分鐘)

**【教學目標】引出 Weaver 作為落實「可觀測性即設計」的關鍵武器，並展示其四大核心能力。**

* **Weaver 的定位：** 它不僅僅是一個靜態檢查工具，而是一個 **致力於將可觀測性設計付諸實踐的 CLI 與平台工具集** 。它讓團隊能夠定義、驗證並演進他們的遙測 Schema。
* **四大核心工作流 (快速預覽)：**
  1. **Registry (註冊表管理)：** 將 Schema 寫成 YAML 檔，並透過 Lint 驗證其語法、語義以及你自訂的策略 (Policies)。這可以強制要求特定欄位為必填，或限制命名前綴。
  2. **Code Generation (產出物生成)：** 搭配 Jinja2 模板，自動將定義好的 Schema 轉換成團隊可以閱讀的 Markdown 說明文件，或是能直接在程式碼中引用的 Go/Rust 語言資料結構。
  3. **Live-checking (動態實時驗證)：** 能夠在開發者的測試階段或 CI 流程中，接收 OTLP 資料流，並即時檢查程式發出的遙測資料是否真的符合 Schema。如果發現違規會直接中斷測試，防止錯誤程式碼上線。
  4. **Emitting (發送範例訊號)：** 在還沒有實際應用程式前，就能根據 Schema 定義產生並發送範例訊號到 OTLP 接收端，方便建立儀表板。
* **總結：** Weaver 將可觀測性從一門「靠工程師自由發揮的藝術」，提升為一門「嚴謹的工程紀律」，這也就是未來兩天我們要深入實作的主題。
