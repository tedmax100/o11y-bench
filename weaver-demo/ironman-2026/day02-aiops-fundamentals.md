# Day2：AIOps 基礎概念——這系列要走去哪裡

昨天做了一件故意的壞事：把 `demo-services` 弄爛，埋進三個命名壞味道。今天不寫任何程式碼，先退一步，把「AIOps 到底是什麼」講清楚——因為接下來 32 天，每一天做的事，都要能回頭對得上今天畫的這張地圖，不然讀者只會看到一堆零散的工具，卻不知道它們合起來要解決什麼問題。

## 如果你去問十個工程師「AIOps 是什麼」

你大概會得到十種答案。有人會說「就是裝一個 AI 幫你看 dashboard，或是邦你查 log 做個摘要分析」，有人會說「是自動化腳本外面包一層聊天介面，你打字問它系統怎麼了」，也有人乾脆說「就是行銷詞，換個包裝賣同一套監控系統」。這些答案都不算錯——市場上確實有一大堆產品長這樣——但它們共同的問題是：都在講「介面長什麼樣子」，沒有一個人講到「這個東西實際上要解決什麼問題」。

要回答這個問題，得先回頭看監控這件事，這些年是怎麼一步步走到今天這個處境的。

## 監控這件事，是怎麼一路演變成今天這樣的

最早，監控系統是給人看的——一張 dashboard、幾個告警閾值，CPU 超過 80% 就叫醒值班的人。這套模式在系統規模還小、服務數量不多的時候運作得很好：閾值是人設的，告警觸發後也是人去看、去判斷、去處理，整條鏈路上每一步都有一個活人的判斷力在把關。

問題是系統會長大。服務從幾個變成幾十個、幾百個，呼叫鏈越疊越深，閾值型告警開始出現一個經典的副作用：告警疲勞。同一個根因會同時炸出十幾個下游服務的告警，值班的人半夜被叫醒十次，有九次都是同一件事的不同症狀。人力沒有跟著系統規模一起長，於是「能不能讓機器先幫忙看一輪」就變成一個很自然的需求——這也是 AIOps 這個詞最早被提出來時，想解決的問題。

但這波需求被市場接住之後，走向了一個岔路：因為「AI 幫你看」這句話本身就很好賣，於是很多產品把力氣花在「介面看起來很聰明」，而不是「機器真的看得懂資料」。這正是文章一開頭那十種答案的來源——「裝一個 AI」、「包一層聊天介面」——都是把力氣花在人機介面，而不是資料本身夠不夠支撐一個機器做`判斷與有效的決策`。

## 認知天花板：為什麼加派人力解決不了問題

這裡想先引用一個我覺得講得很準的說法，來自《代理式可靠性工程》（Agentic Reliability Engineering，ARE）這本書的第一章。書裡描述了一個很多人應該都經歷過的場景：半夜三點，值班工程師被叫醒，面對一個已經過載的系統，一邊還在睡意裡，一邊要判斷這十幾個告警裡哪一個是根因、哪些只是連帶反應。書裡指出，SRE 這個角色長期以來真正卡住的地方，從來不是技術或流程不夠成熟，而是一個「認知天花板」——**再多的自動化都無法移除它，因為自動化擴展的是「執行」，不是「判斷」**。

這句話值得多停留一下。過去十年`可觀測性領域`做的所有事——更細的指標、更完整的 trace、更快的查詢——本質上都是在讓「執行」這件事變快：資料更快被撈出來、圖更快被畫出來。但「看著這些資料、判斷根因是什麼、決定下一步該做什麼」，這個判斷的動作，從頭到尾都還是壓在一個人的腦子裡，而人的判斷力不會因為系統多裝了幾個 dashboard 就跟著變快。告警疲勞正是這個天花板最直接的症狀：閾值設定的依據，從來不是「怎樣的閾值能幫出最好的決策品質」，而是「一個人一個晚上能承受幾次被吵醒」。這是為了保護人的注意力預算而妥協出來的數字，跟資料本身該不該在那個時間點觸發告警，其實是兩件事。

## 真正卡住的地方，其實是資料，不是模型

回頭看可觀測性資料原本是怎麼設計的：圖表是為了視覺化的模式辨識而調校的，告警閾值是照著人類的注意力預算校準的，連 runbook 都是寫成一段一段給人讀的散文，假設讀的人本身就帶著組織裡的背景知識——一個資深 SRE 看到一條延遲曲線往上翹，會自動聯想到「這個服務上週剛上線一個新版本」「這個時間點是不是有排程任務在跑」，這些上下文從來不在圖表裡，是這個人腦子裡的。

現在把「看圖表的人」換成一個 machine consumer（agent 或 LLM），問題就浮出來了。書裡有個比喻我覺得很傳神：機器代理讀這一整套為人設計的觀測堆棧時，**表現得就像一位極為聰明的新人第一天上班**——他可能反應很快、邏輯很清楚，但完全沒有組織脈絡，不知道「這個服務三個月前發生過一次類似的事」「這個 team 的命名習慣跟那個 team 不一樣」。具體拆開來看，缺的是三件事：缺語意（一個 attribute 叫什麼、代表什麼，前後服務講不講同一種語言，這正是昨天 Day1 那三個壞味道的根源）、缺情境（一條 trace、幾個 metrics 數字、幾條 log，彼此的關聯是機器自己腦補去查出來的，不是資料本身就講好的故事）、缺信任度（機器說「我有 80% 信心是這個根因」，這句話本身要怎麼被驗證，資料裡從來沒有這個機制）。

## 「缺語意」到底缺的是什麼

這三塊裡，「缺語意」聽起來最抽象，但其實是最基礎、也最先要處理的一塊，值得多花點篇幅講清楚，因為接下來 Day8-18 整段治理基礎建設，本質上都是在補這一塊。

先把「語意」這個詞從「格式」裡拆出來。一個 attribute 能不能被程式解析、型別對不對、JSON schema 過不過，這是**格式**——機器很擅長檢查格式，這也是大部分工具本來就在做的事。但「這個 attribute 代表的意思，是不是跨服務、跨團隊都指同一件事」，這是**語意**——格式檢查完全抓不到這件事。回頭看昨天的三個壞味道，會發現它們剛好對上語意出問題的三種典型樣子：

第一種，**同一個概念，兩個名字**。`order` service 裡的 `user_id` 跟另一層悄悄轉換前的 `userId`，指的其實是同一個使用者，但因為命名不同，一個機器代理如果只是照字面比對，會把它們當成兩個不相干的欄位——它沒有能力知道「這兩個字串，其實在講同一件事」，除非有人先把這個對應關係講清楚。

第二種，**同一個名字，語意隨時間漂移**。這個系列還沒特別舉過這個例子，但在真實團隊裡很常見：一個 `status` 欄位，一開始只有 `success`/`failed` 兩種值，後來某個服務為了描述「正在重試中」這個新狀態，直接加了一個 `retrying`，卻沒有同步通知其他讀這個欄位的下游服務。下游那些用「非 `success` 就是失敗」邏輯寫死的告警規則，從此開始把「正在重試、還沒真正失敗」的請求，誤判成失敗——**欄位名稱沒變，但它背後代表的意義變了**，這種漂移比欄位改名更難察覺，因為連 schema diff 這種工具，第一時間都看不出「值域的意義」被動過手腳。

第三種，**span/事件本身沒有業務語意，只有技術語意**。昨天壞味道二提到的 `POST /api/orders` 就是這種——它精準描述了「發生了什麼 HTTP 動作」，卻完全沒講「這在業務上是什麼事」。這不是欄位對不對的問題，而是**這個資料點本身，是用技術詞彙描述的，不是用業務詞彙描述的**，而 agent 要做的判斷，往往得先落在業務語意的層次（這是不是一次結帳失敗？），再往下才會去查技術細節。

這三種樣子背後，其實指向同一件事：**語意是一份「共同的約定」，而不是任何一個欄位、任何一個服務單獨能決定的東西**。一個團隊自己內部怎麼命名，只要自己看得懂，永遠都不算錯；但只要這份資料要被別的服務讀、被別的團隊查、被一個機器代理拿來跨服務關聯判斷，命名跟意義是否一致，就從「個人喜好」變成了「治理問題」。這正是為什麼接下來 Day8 開始會介紹 semantic convention 跟 Weaver registry——它們要做的事，說到底就是把「這份共同約定」寫下來，變成一份機器可以拿去核對的規格，而不是只存在每個資深工程師的腦子裡、靠口耳相傳。

昨天 Day1 講的所有壞味道，其實都是「缺語意」這一類問題的具體案例；接下來 Day19-26 的 Signal Plane、Day31 的 rubric 驗證機制，分別對應的正是「缺情境」跟「缺信任度」這兩塊。AIOps 真正要解決的問題，從來不是「換一個更聰明的模型」，而是「把資料本身，準備成機器不用腦補就能拿來做判斷的樣子」——ARE 書裡把這種為機器決策而設計的資料，稱作**決策級遙測（decision-level telemetry）**：訊號從一開始就是為了「必須做決策的對象」而設計，裡面會包含語意豐富化的內容、把依賴關係圖當成第一級資料（而不是事後才去反推拓撲）、以及誰擁有這份資料、這份資料的意圖是什麼的結構化說明。這個詞會在 Day25 正式展開，今天只需要先有個印象：這不是把現有的圖表包一層 AI，而是從資料設計的源頭就重新想過一遍。

有了這幾個名詞，也能重新回答可靠性這件事該怎麼被衡量。過去我們習慣用 uptime（正常運行時間）當作唯一指標，但當系統裡開始有機器代理在做判斷時，光看結果夠不夠好已經不足夠——真正該問的是「系統在通往這個 uptime 結果的路上，沿途做的每一個判斷，品質好不好」。這也是 ARE 後面會定義出幾個旗艦級 SLO（像 ARR、DQ-SLO 這類）的原因，這系列不會用到那麼深的地方，但這個「衡量判斷品質，而不只是衡量結果」的視角，值得先放進今天的地圖裡。

## 這系列要做的 AIOps，明確劃在哪一段

把這個問題釐清之後，還有一件事要先講清楚：即使資料準備好了，「讓 agent 讀懂資料、給出判斷」跟「讓 agent 自己動手執行、自己從錯誤中學習校正」，是兩個完全不同量級的問題。後者需要一整套治理機制——授權層級、信任天花板、校準誤差的量測——這些機制光是定義清楚就得花上好幾天，硬要塞進同一個系列，只會變成每一天都在鋪陳一個 30 天後才會收斂的概念。

所以這系列刻意分成兩段：**Series 1（這 34 天）只做到「讓 agent 讀懂決策級事件、給出有信心分數的判斷、給出下一步建議」，不做「agent 能不能自主執行」「agent 能不能自我學習校正」**——那些留給 Series 2 的治理平面跟校準機制。這條線不是藏著不講，而是刻意畫出來、大聲講出來的：一個誠實的系列，應該讓讀者知道它現在做到哪一步、還沒做到哪一步，而不是用一個漂亮案例掩蓋還沒做完的部分。

## 接下來 32 天的地圖

從今天算起，Series 1 剩下的內容分兩大段。第一段（Day3-18）是治理基礎建設：介紹 OTel Operator 怎麼把「各自安裝」變成中央調和、Weaver 怎麼定義規範並在 CI 階段攔下違規，直接對應昨天壞味道一、三的根因。第二段（Day19-34）是讓資料真正能被 agent 拿來推理：先補上拓撲圖、把訊號噪音降下來、疊上情境豐富層，最後才輪到 agent 本身怎麼決策、怎麼被驗證信心分數、怎麼給出下一步的建議。

今天要記住的只有一句話：**接下來每一天做的事，都是在把「一份只給人看的可觀測性資料」，一步步變成「一份機器不用腦補也能拿來做判斷的資料」**。明天開始，會正式進到第一段——先從 OTel Operator 這個 k8s operator 為什麼特別適合平台團隊講起。
