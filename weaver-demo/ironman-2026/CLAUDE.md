# 鐵人賽文章的寫作風格

這個目錄是 2026 鐵人賽《AIOps with OpenTelemetry》的文章。寫或改這裡的 `dayNN.md` 時，照這份風格，不要照一般技術文件的寫法。

基準範例是 `day01-ungoverned-baseline.md` 跟 `day02-aiops-fundamentals.md`（敘事與原理的骨架），以及 `day07.md`–`day10.md`（實測與結構化說明的密度）。一篇好的文章是這兩者的合併，不是二選一。

## 骨架：先原理，再結構，最後才是操作

每一篇都照這個順序走，不要一開頭就貼指令：

1. **先講為什麼**——這個問題在真實團隊裡怎麼長出來的、為什麼靠現有做法擋不住。用情境跟時間推進來寫（「試著把時間拉回這些決定發生的當下」），不要用「本文將介紹…」。
2. **再講結構**——這個機制內部怎麼分工、資料怎麼流動。這一段要有圖（見下），讓讀者拿到一張可以掛後續細節的地圖。
3. **最後才是操作**——指令、YAML、真實輸出，用來驗證前兩段講的東西。

## 每一篇的必備元素

- **回指與預告**：開頭一句回指前一天做了什麼、為什麼今天接這個；結尾一句預告明天。中段提到某個概念時，明確寫「Day14 會展開」而不是含糊帶過。
- **「今天沒做的事」收尾段**：誠實列出刻意留給後面的東西跟原因。這是這系列的招牌，不要省略。
- **範例要多、要有變化**：同一個概念給多個角度的例子（不同 `type`、不同嚴重度、成功跟失敗各一），不要只給一個最小可行範例就跳過。
- **所有輸出都要是真跑出來的**。不確定就去跑一次，不要憑印象寫。版本會變、行為會變。

## 圖：用 mermaid，而且要有結構性

每篇至少 2–4 張圖，用來承載「結構」而不是裝飾：

- `flowchart` 畫管線、分支、決策樹（「什麼情況走哪條路」）
- `classDiagram` 畫巢狀結構與引用關係（manifest → file → group → attribute）
- `sequenceDiagram` 畫時間順序與互動（CI gate、常駐監聽 vs 跑一次）
- `stateDiagram-v2` 畫流程的狀態轉換（草稿 → 規範）

節點標籤裡換行用 `<br/>`，**不要用 `\n`**（不會渲染）。`classDiagram` 的 `class X["中文標籤"]` 語法在舊版 mermaid 上會掛，優先用 `flowchart` 代替。

## 語氣與句法

- 用完整段落敘事，不要把內容壓成一堆條列。條列只用在真正平行的清單。
- 一段最多一個粗體句，用來標記那段的重點結論。
- 表格用在「多維度對照」（前後對照、多個情境的結果比較），不要用表格取代解釋。
- 中文為主，技術名詞保留英文原文（`attribute`、`registry`、Finding、semantic convention），不要翻譯成「屬性群組」這類自創詞。
- 讀者已經懂 observability stack（Prometheus/Loki/Tempo/Grafana、OTel 基本概念），不用解釋這些；LLM／eval／agent 相關的概念才需要展開。

## 踩到的坑就是內容，不是雜訊

這系列最有價值的段落幾乎都來自「真的踩到」的東西——`-r .` 的假綠燈、policy 只比對名字前綴、`infer` 還原不出 `brief`。寫到這種東西時：

- 完整寫出「表面看起來沒事、實際上出了什麼問題」，附真實輸出當證據
- 把它連回這系列的主軸（治理 → 資料可信度 → agent 判斷），不要只當成工具 bug 記一筆
- **不要為了讓文章漂亮而修掉這些坑**。一個「檢查通過但其實是錯的」的案例，比三個都成功的案例有用

## AIOps 主軸要一路帶著

這不是一個純 Weaver 教學系列。每一天的治理動作，都要能回答「這對後面 agent 的判斷品質有什麼影響」。例如講 `enum` 的 `members` 時，要點出那是 LLM 唯一能事先知道 label 值域的來源；講 schema 一致性時，要連回 Day2 的「缺語意」。沒有這條線，文章會退化成工具手冊。

## 對應的程式碼放 submodule

可執行的範例、policy、registry 放 `otel-aiops-agent/dayNN/`（submodule），文章只貼重點片段跟真實輸出，並在開頭連過去。submodule 的 `dayNN/README.md` 寫完整重現步驟。
