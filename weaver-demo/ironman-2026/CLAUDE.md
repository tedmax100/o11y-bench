# 鐵人賽文章的寫作風格

這個目錄是 2026 鐵人賽《AIOps with OpenTelemetry》的文章。寫或改這裡的 `dayNN.md` 時，照這份風格，不要照一般技術文件的寫法。

基準範例是 `day01-ungoverned-baseline.md` 跟 `day02-aiops-fundamentals.md`（敘事與原理的骨架），以及 `day07.md`–`day10.md`（實測與結構化說明的密度）。一篇好的文章是這兩者的合併，不是二選一。

## 骨架：先原理，再結構，最後才是操作

每一篇都照這個順序走，不要一開頭就貼指令：

1. **先講為什麼**——這個問題在真實團隊裡怎麼長出來的、為什麼靠現有做法擋不住。用情境跟時間推進來寫（「試著把時間拉回這些決定發生的當下」），不要用「本文將介紹…」。
2. **再講結構**——這個機制內部怎麼分工、資料怎麼流動。這一段要有圖（見下），讓讀者拿到一張可以掛後續細節的地圖。
3. **最後才是操作**——指令、YAML、真實輸出，用來驗證前兩段講的東西。

## 每一篇的必備元素

- **回指與預告**：開頭一句回指前一天做了什麼、為什麼今天接這個；結尾一句預告明天。中段提到某個概念時，明確寫「Day14 會展開」而不是含糊帶過。
- **「今天沒做的事」收尾段**：誠實列出刻意留給後面的東西跟原因。這是這系列的招牌，不要省略。
- **範例要多、要有變化**：同一個概念給多個角度的例子（不同 `type`、不同嚴重度、成功跟失敗各一），不要只給一個最小可行範例就跳過。
- **所有輸出都要是真跑出來的**。不確定就去跑一次，不要憑印象寫。版本會變、行為會變。

## 圖：用 mermaid，而且要有結構性

每篇至少 2–4 張圖，用來承載「結構」而不是裝飾：

- `flowchart` 畫管線、分支、決策樹（「什麼情況走哪條路」）
- `classDiagram` 畫巢狀結構與引用關係（manifest → file → group → attribute）
- `sequenceDiagram` 畫時間順序與互動（CI gate、常駐監聽 vs 跑一次）
- `stateDiagram-v2` 畫流程的狀態轉換（草稿 → 規範）

節點標籤裡換行用 `<br/>`，**不要用 `\n`**（不會渲染）。`classDiagram` 的 `class X["中文標籤"]` 語法在舊版 mermaid 上會掛，優先用 `flowchart` 代替。

## 語氣與句法

- 用完整段落敘事，不要把內容壓成一堆條列。條列只用在真正平行的清單。
- 一段最多一個粗體句，用來標記那段的重點結論。
- 表格用在「多維度對照」（前後對照、多個情境的結果比較），不要用表格取代解釋。
- 中文為主，技術名詞保留英文原文（`attribute`、`registry`、Finding、semantic convention），不要翻譯成「屬性群組」這類自創詞。
- 讀者已經懂 observability stack（Prometheus/Loki/Tempo/Grafana、OTel 基本概念），不用解釋這些；LLM／eval／agent 相關的概念才需要展開。

## 踩到的坑就是內容，不是雜訊

這系列最有價值的段落幾乎都來自「真的踩到」的東西——`-r .` 的假綠燈、policy 只比對名字前綴、`infer` 還原不出 `brief`。寫到這種東西時：

- 完整寫出「表面看起來沒事、實際上出了什麼問題」，附真實輸出當證據
- 把它連回這系列的主軸（治理 → 資料可信度 → agent 判斷），不要只當成工具 bug 記一筆
- **不要為了讓文章漂亮而修掉這些坑**。一個「檢查通過但其實是錯的」的案例，比三個都成功的案例有用

## AIOps 主軸要一路帶著

這不是一個純 Weaver 教學系列。每一天的治理動作，都要能回答「這對後面 agent 的判斷品質有什麼影響」。例如講 `enum` 的 `members` 時，要點出那是 LLM 唯一能事先知道 label 值域的來源；講 schema 一致性時，要連回 Day2 的「缺語意」。沒有這條線，文章會退化成工具手冊。

## 治理要用 platform engineering 的角度收

主軸是治理，但「治理」這個詞很容易寫成一種**由上而下的管制**——寫出來的文章會像在教一個中央團隊怎麼多設幾道關卡。這系列要刻意站在另一個位置：治理是**平台團隊提供給產品團隊的能力**，registry、CI gate、policy 都是內部平台的介面，而不是稽核清單。

每一天除了「這個機制怎麼運作」，還要能回答下面這幾個問題中的至少一個。不必每篇都全部答（也不要寫成問答式的條列），但一篇如果一個都答不出來，就代表它只寫了工具、沒寫工程：

- **誰維護、誰使用。** 這個 registry／policy／workflow 是平台團隊擁有的，還是每個產品團隊各自一份？改它需要誰同意？（Day13 的分層就是這個問題的機制化：哪一層統一、哪一層放手。）
- **產品團隊要付多少成本。** 一個新服務要接上這套治理，實際要做的事有幾件、要學幾個新概念？如果答案是「先讀完 registry 規格」，那這個設計就把成本推給了使用者。
- **失敗的時候，錯誤訊息夠不夠讓對方自己修好。** 這是治理能不能規模化的分水嶺：一道 gate 如果擋下來之後還要平台團隊親自去解釋，它的維護成本會隨團隊數線性成長。所以文章裡看到「訊息誤導」「annotation 落不到行上」「panic 沒有診斷」這類坑時，要明確寫出它的 platform 代價，不要只當成 UX 抱怨。
- **這條規則是強制、預設、還是建議。** 對應到三層驗證模型：hard error 是強制，`--future` 是平台團隊替所有人做的一個時程決定，Rego policy 是可以按團隊分級的。paved road 的重點從來不是「只有一條路」，是「預設那條路最好走，要走別條得自己說明理由」。
- **演進的責任在哪一邊。** base 改版時，是平台團隊負責通知並提供遷移期，還是產品團隊自己發現？（Day14 那個「deprecation 是宣告、不是通知」就是這個問題的具體形狀。）

語氣上要注意兩件事。一，**不要用「規範」「強制」當形容詞去描述整個系列的目標**——這系列真正主張的是「讓對的事情比錯的事情好做」。二，治理的成本要誠實寫，包含平台團隊自己的成本（多維護一份 policy、多釘一個版本、多一個要回答的問題），不要只寫產品團隊被擋下來的部分。

這個角度跟 AIOps 主軸是同一條因果鏈的兩端：**平台團隊把治理做成好用的介面 → 產品團隊真的照做 → 遙測資料一致可信 → agent 的判斷才有依據。** 中間任何一環是靠人盯著，這條鏈就斷了。所以「能不能自動化」跟「能不能被 agent 消費」在這系列裡是同一個標準的兩種說法。

## 對應的程式碼放另一個 repo

可執行的範例、policy、registry 放 `otel-aiops-agent/dayNN/`，文章只貼重點片段跟真實輸出，並在開頭連過去，該 repo 的 `dayNN/README.md` 寫完整重現步驟。

**文章裡不要出現「submodule」這個詞**——那是我這邊的工作方式，讀者只會看到 GitHub 上的一個 repo。開頭的連結一律寫成「程式碼在範例 repo [`OTel_AIOps_Agent`](網址) 的 [`dayNN/`](網址)」，指令的前提寫「從 repo 根目錄跑」。

**資料夾日號不跟著文章重編**（v5 把 16 篇併成 12 篇之後）：`dayNN/` 存的是每一天當下那組 stack 的完整快照，重編會失去時間順序、合併的那幾天也會撞在一起。所以文章 DayN 對應的資料夾可能是別的號碼，第一次提到時說明一句就好。

**那個 repo 的佈局要寫對**（曾經寫錯過）：

- 那個 repo 裡**沒有** `demo-services/` 這個目錄。它存的是每一天當下那組 stack 的**完整快照**，一天一個資料夾：`dayNN/services/{api-gateway,order,payment,user,webapp}`、`dayNN/shared/`、`dayNN/k8s/`、`dayNN/weaver/`。
- `demo-services/` 是**主 repo** `o11y-bench/` 底下的目錄，是這組服務持續演進的地方。文章裡用 `demo-services` 稱呼這組服務沒問題（Day1 就是這樣介紹的），但**不要說它在範例 repo 裡**，也不要寫成那個 repo 的路徑。
- 文章裡的指令一律假設在範例 repo 的根目錄下跑，路徑從 `dayNN/` 開始寫（`-r day06/weaver/registry`），不要寫裸的 `weaver/registry`——那在根目錄下不存在。
- 貼路徑之前先 `ls` 確認一次。這類錯誤讀者一照做就會撞到。
