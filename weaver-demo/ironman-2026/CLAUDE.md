# 鐵人賽文章的寫作風格

這個目錄是 2026 鐵人賽《AIOps with OpenTelemetry》的文章。寫或改這裡的 `dayNN.md` 時，照這份風格，不要照一般技術文件的寫法。

基準範例是 `day01.md` 跟 `day02.md`（敘事與原理的骨架），以及 `day07.md`–`day10.md`（實測與結構化說明的密度）。一篇好的文章是這兩者的合併，不是二選一。

**聲音的部分改吃 [`ref_blogs/writing-style.md`](../../ref_blogs/writing-style.md)**（從過去五篇鐵人賽日誌萃取出來的）。那份講的是「聽起來像不像本人」，這份講的是「這個系列的結構、證據標準、平台工程角度」。兩份一起用，下面「聲音：雙聲道」那節列了合併之後的結論，衝突處以這份為準。

## 骨架：先原理，再結構，最後才是操作

每一篇都照這個順序走，不要一開頭就貼指令：

1. **先講為什麼**——這個問題在真實團隊裡怎麼長出來的、為什麼靠現有做法擋不住。用情境跟時間推進來寫（「試著把時間拉回這些決定發生的當下」），不要用「本文將介紹…」。
2. **再講結構**——這個機制內部怎麼分工、資料怎麼流動。這一段要有圖（見下），讓讀者拿到一張可以掛後續細節的地圖。
3. **最後才是操作**——指令、YAML、真實輸出，用來驗證前兩段講的東西。

## 每一篇的必備元素

- **回指**：開頭一句回指前一天做了什麼、為什麼今天接這個。這一句要具體（「昨天那隻 agent 拿了 4.5/9」），不要寫成「延續昨天的主題」。結尾可以提一句明天的方向，但不要承諾細節（見下面「交叉引用不要寫死日號」）。
- **「今天沒做的事」收尾段**：誠實列出刻意留給後面的東西跟原因。動手日必寫；純概念日沒有實作可留白時可以省略，收成一段短「總結」就好。列的時候只寫「留給後面」，不要標第幾天。
- **範例要多、要有變化**：同一個概念給多個角度的例子（不同 `type`、不同嚴重度、成功跟失敗各一），不要只給一個最小可行範例就跳過。
- **所有輸出都要是真跑出來的**。不確定就去跑一次，不要憑印象寫。版本會變、行為會變。

## 圖：用 mermaid，而且要有結構性

每篇至少 2–4 張圖，用來承載「結構」而不是裝飾：

- `flowchart` 畫管線、分支、決策樹（「什麼情況走哪條路」）
- `classDiagram` 畫巢狀結構與引用關係（manifest → file → group → attribute）
- `sequenceDiagram` 畫時間順序與互動（CI gate、常駐監聽 vs 跑一次）
- `stateDiagram-v2` 畫流程的狀態轉換（草稿 → 規範）

節點標籤裡換行用 `<br/>`，**不要用 `\n`**（不會渲染）。`classDiagram` 的 `class X["中文標籤"]` 語法在舊版 mermaid 上會掛，優先用 `flowchart` 代替。

**指涉圖裡的節點時，用節點的文字，不要用它的位置。** 寫過「最右下那一支」「最下面那個框」，結果一個是 `flowchart TB` 排版不保證、另一個根本是 `flowchart LR`（那個框其實在最右邊）。mermaid 的版面是自動算的，換渲染器就跑掉，讀者對著圖找不到你說的位置。改成「圖裡 `ref` 那一支」「『沒有任何一層檢查這個數字的來源』那個框」。

## 語氣與句法

- 用完整段落敘事，不要把內容壓成一堆條列。條列只用在真正平行的清單。
- 一段最多一個粗體句，用來標記那段的重點結論。
- 表格用在「多維度對照」（前後對照、多個情境的結果比較），不要用表格取代解釋。
- 中文為主，技術名詞保留英文原文（`attribute`、`registry`、Finding、semantic convention），不要翻譯成「屬性群組」這類自創詞。
- **縮寫在每一篇的內文第一次出現時要展開一次**（OTel = OpenTelemetry、ARE、CRD、CR、SLO…）。標題可以直接用縮寫，但內文不能假設讀者從標題推得出來——每篇都是獨立入口，讀者不一定從 Day1 看起。展開一次就好，後面照用縮寫。
- **CLI 的短旗標同理，第一次用要說它是什麼**（`-r` = `--registry`、`-p` = `--policy`）。它們常常第一次出現是在程式碼區塊裡，很容易漏掉——而讀者後面看到「這個參數的兩個方向都很危險」時會完全接不上。
- **不要用還沒介紹過的系列自創詞去預告**（曾經犯過：Signal Plane、決策級遙測 在正式登場前就被拿來當「後面會做的事」的代名詞）。前指沒問題，前引會讓讀者卡住——他不知道那是什麼，也查不到，因為那是這系列自己的詞彙。預告的時候用白話講那件事本身（「讓另外兩種訊號也自帶足夠的上下文」），等到真的展開那天再把名字給它。
- 讀者已經懂 observability stack（Prometheus/Loki/Tempo/Grafana、OTel 基本概念），不用解釋這些；LLM／eval／agent 相關的概念才需要展開。

## 要像人在講話，不是像文件

這是最容易寫壞的一項：**內容對、結構對，但讀起來像產品文件，就是失敗的稿子。** 判準是「這段話唸出來像不像一個工程師在跟同事解釋」。以 Day1 定稿為基準，具體做法：

- **用口語的轉折當段落接縫**，不要用「本節將說明」「綜上所述」。像「但細想會發現現在的 agent 有些限制跟問題在︰」「到這，事情只是查詢條件寫錯了。但真正的問題是它拿著三個空結果，最後說出了什麼」。
- **把自己的反應留在文字裡。** 「這隻 agent 錯得很穩定（笑）」「當時我覺得這是一次成功的 prompt engineering」——情緒跟事後回看的懊悔都是內容的一部分，不要修掉。
- **每個技術發現都要落到「值班的人會怎樣」。** Day1 那段是範本：系統出問題的當下會很混亂、人也會緊張，若錯信這錯誤的資訊做出錯誤處置會很危險；若還要人花時間判斷真偽，那還不如直接讓工程師人工排查。**沒有這種段落，技術發現就只是一則趣聞。**
- **「我們」講共同的實務，「我」講自己的判斷與踩的坑。**
- **不要自創沒有英文對應的術語。** 曾經寫過「判官守門」，被問「英文是什麼」而答不出來——那就是這個詞不該存在的證據。直接用 LLM-as-a-judge、grader、guardrail、verifier。
- **先用這個語氣寫初稿**，不要先寫一份乾淨的文件再回頭「加口語」，那樣改不回來。

### 四個會讓稿子讀起來像 AI 寫的習慣（Day3 全篇重寫時抓出來的）

內容正確、結構正確，但被退稿的原因通常是這四個。寫初稿時就避開，不要指望回頭改。

1. **破折號當萬用連接詞。** 這是最明顯的一個。Day3 初稿 313 行裡有 31 個 `——`，幾乎每段都是「一段敘述 `——` 一句粗體結論」，同一個模子印出來的。**一篇最多留一兩個**，其他改成句號斷句、逗號接續，或乾脆拆成兩句話。中文本來就很少這樣用破折號。
2. **每段結尾都用粗體收一句。** 粗體變成節奏的一部分就失效了，讀者會全部略過。**一節大概一個粗體**，留給真的要記住的那句。
3. **老師口吻。** 「這裡值得停一下」「值得注意的是」「這一點很關鍵」——改成「我多講一句」「這個我踩過」，或者直接講內容，不要先預告自己要強調了。
4. **整齊的排比。** 「不同團隊、不同語言、不同廠商」「一是…二是…三是…」。真的是平行清單才排比，不然就讓句子長短不一，人講話不會這麼整齊。
5. **宣告自己很誠實。** 「而這裡我得誠實記一筆」「我得誠實講」「這裡要誠實地說」——**沒有人這樣講話。** 誠實是靠直接把難堪的事實寫出來達成的，不是靠先宣告一句。要講就直接講：「不過我那份 CR 根本沒寫 `image`」「但這份清單不是任何形式的防護」。同一類要避開的還有「值得一提的是」「不得不說」「必須指出」這種先替讀者決定重要性的開場。

## 我改稿時每次都會加的東西（Day2 定稿歸納）

寫初稿時就照做，不要等我回頭補。

- **用 `>` blockquote 放旁白。** 正文負責論證，blockquote 放三種東西：一句自己的經驗（「我曾經以為有了 AI，很多排查新興問題的動作都能交給 AI，但實施下去發現想的太美好了」）、一個誠實的成本提醒（「越豐富的上下文內容，往往伴隨著更多的儲存成本跟網路頻寬」）、一條延伸閱讀連結（o11y 2.0 的 wide structured log）。**正文不要為了塞這些而變長，把它們降一層。**
- **抽象名詞第一次出現時，用反引號標起來。** 不只程式碼識別字——`組織脈絡`、`缺語意`、`上下文內容`、`無歧義` 都要。這是我用來標記「這個詞等一下還會再用」的視覺記號。
- **抽象詞要立刻給一句大白話翻譯，可以用俗語或歌詞。** 「這是**語意**，格式檢查完全抓不到︰廣義點白話點講`無歧義`（你說的黑不是黑，你說的白是什麼白）。」——沒有這句，讀者記不住那個詞。
- **情緒用口語標記，不要只用括號註記。** 「（包括我 QQ）」比「（包括去年的我）」更接近我的語氣。
- **引用書或文章一定附連結**，並且指稱要完整（「ARE 這本書裡」，不要只寫「ARE 裡」，ARE 這個縮寫還有別的同名東西）。連結的完整規則見下面「引用與連結」。
- **句子寧可鬆一點也不要為了精簡而變硬。** 我會把「沒有一件是把模型換大就會消失的」改成「沒有一件事情，是把模型換大換更強就會消失的」。念起來像在講話比字數少重要。

## 聲音：雙聲道

`ref_blogs/writing-style.md` 抓到的最重要一件事：**正文是工整的推進，blockquote 是真心話頻道。** 兩層並存才像本人寫的，只有正文那層就會退回產品文件。下面是套進這個系列之後的具體做法。

### 開場

第一段是 blockquote 金句，三到五行，短句換行、不用句號結尾。它講的是今天這篇的立場，不是摘要：

```
> 一個查得到資料的 agent
> 跟一個查得對的 agent
> 中間隔的不是模型大小
```

金句之後才接回指前一天那句（具體，「昨天那隻 agent 拿了 4.5/9」），再接程式碼 repo 的連結。

### 中段

每 2~3 個 H2 插一段 blockquote，放正文不方便講的東西，四種用途照 `writing-style.md`：業界慘案（「舉個現實案例，…」起手）、吐槽、自己的經驗、成本提醒。**正文不要為了塞這些而變長，把它們降一層。**

### 收尾

`## 小結` 用「總結來說，」起手，然後**小結之後一定要有一段文末彩蛋 blockquote**：自嘲、預告明天的方向（不寫日號）、或補一條延伸閱讀。

### 語氣的幾條硬規則

- **自降姿態，不當權威。** 一篇至少一處自嘲或示弱（「我當時以為這是一次成功的 prompt engineering」「這段我來回試了三次才對 QQ」）。禁止「你必須」「最佳解就是」「顯然」。要斷言時先用「其實」「往往」「肯定」鋪墊。
- **顏文字有分工，一段最多一個，而且要落在情緒轉折點**：`XD` 自嘲或指出荒謬、`:)` 軟化的宣告、`:(` 承認疏漏、`QQ` 示弱、`^^` 講到錢或老闆、`！！` 災難場面。
- **高頻起手式**：其實／往往／通常／肯定／白話點，…／舉個現實案例，…／總結來說，…／所以…。
- **本人的寫法**：「嘛」不寫「嗎」、「幹麻」不寫「幹嘛」。
- **口語直出感比工整重要。** 「是也能搭配 Push 模式…但都不如 Pull 來的適合」這種語序不要改成標準書面語。但錯字不要學。
- **反模式的靶子可以直接沿用** `writing-style.md` §9 那份清單（「先做再說」的團隊、只看涵蓋率、疊床架屋、上雲照搬地端、出事只會加 log 再等、工具買一堆關聯不起來）。反諷句型：「這種我只能說『很棒！』」。

### 這些仍然以本檔為準（`writing-style.md` 沒管到或講得比較鬆的）

- 破折號 `——` **一篇最多一兩個**。
- 一節大概一個粗體。
- 不要整齊排比、不要老師口吻、不要宣告自己很誠實。
- 不要自創沒有英文對應的術語。
- 小結不要寫成總結報告：不要排比、不要用力的金句。「總結來說」起手之後講的是今天的侷限跟下一步的實際用途（見下面「小結怎麼寫」）。

## 引用與連結

OTel 這個領域的好處是幾乎每件事都查得到官方出處，不管是 spec、repo 裡的 YAML，還是 OTel blog。所以這系列的標準是：**除了自己實測的東西，其他事實宣稱都要能點到來源。**

### 什麼要給連結

版本狀態、預設行為、規格條文、數字、上游進度，只要不是自己跑出來的，就附連結。自己實測的不用連結，但要標環境（「驗證環境：weaver 0.25.1、semantic-conventions `c6cda02`」），這條跟前面「所有輸出都要是真跑出來的」是同一件事的兩面。

來源的優先順序：官方 repo 的原始碼最高，其次是官方 spec 文件，再來是 OTel blog，最後才是二手文章。講 semconv 的行為時，直接連到那個 YAML 或 JSON Schema，比連一篇轉述的部落格有力得多。

### 連結要 pin 版本

引官方 YAML 或程式碼時用 tag 或 commit，不要用 `main`。文章裡的行號和數字是寫的當下數出來的，`main` 三個月後就對不上，讀者點進去會發現你在講一個不存在的東西。

- 用 `.../blob/v1.37.0/model/hardware/fan-metrics.yaml`
- 不要用 `.../blob/main/model/hardware/fan-metrics.yaml`

例外是你要講的正是「現在的 main 長怎樣」，那就寫明是哪一天看的。

### 不要猜路徑

聽起來很合理的路徑不代表存在。已經確認 404 的：

- `open-telemetry/weaver/blob/main/docs/semconv-syntax.md`
- `open-telemetry/semantic-conventions/blob/main/model/syntax.md`

貼之前開一次，跟前面「貼路徑之前先 `ls` 確認一次」是同一個習慣，只是對象換成網址。

### 說清楚數字是哪來的

這個比連結本身更有用。寫出一個數字時，順手交代它的來源等級，讀者才知道要多信它：

> （這份清單是從 `semconv.schema.v2.json` 的 `properties` 直接讀出來的，不是猜的。）

一篇至少用一次。尤其是文章的核心數字，例如「24 / 250 個檔案」「上游有 100 個屬性沒填 `role`」這種，讀者第一個反應就是「你怎麼知道的」，先把 `grep` 或 resolve 的指令貼出來會省掉很多懷疑。

### 連結要融進句子

行內連結，不要在文末堆一份參考資料清單。寫成「官方那篇 [Observability by Design](網址) 把『把遙測當成 public API』這個立場講得很清楚」，而不是「參考：[1] Observability by Design」。圖片同理，下一行補「圖片參考自 [來源](網址)」。

### 交稿前掃一次

```bash
# 找出提到版本號、百分比、數量但整段沒有連結的地方
grep -nE "[0-9]+\s*(個|%|次|行)" dayNN.md | grep -v "http"
```

## 小結怎麼寫（Day4 定稿的範例）

小結本身**不要用力**，用力的話留給它後面那段彩蛋 blockquote。以 Day4 那段為基準（起手補上「總結來說」）：

> 總結來說，今天的分享其實跟 AIOps 沒太多關係，但是透過 OTel operator 能快速且以統一的形式，替各部門的服務快速注入 OTel 產生 signal 的能力。對於沒接觸過得部門來說，trace 是他們很容易為之一亮的事物。且至少有全鏈路覆蓋的 trace，會對於我們之後利用 trace 資料做成`靜態的系統圖譜 model` 會更方便。

它做對三件事：

1. **先承認今天的侷限**（「其實跟 AIOps 沒太多關係」）。硬把每一天都拉回主軸會讓讀者不信任你，坦承反而讓後面那句連結有份量。
2. **講人的反應，不是技術價值**（「trace 是他們很容易為之一亮的事物」）。這回答了「平台團隊為什麼推得動」，是規格表寫不出來的東西。
3. **最後一句給下一步的實際用途**，而不是抽象宣言。「之後做成系統圖譜會更方便」比「這關乎資料可信度」具體得多。

反面是我寫過的版本：「這就是為什麼這系列不能只做把 agent 教聰明⋯⋯」，一個很用力的結論句，粗體、排比、金句都齊了，但那不是人在分享，是在做總結報告。**小結前面也不要先放一段用力的收尾**，會跟小結打架。

小結之後接一段彩蛋 blockquote，就一兩句，自嘲或預告明天的方向：

```
> 這篇的 policy 我來回改了五版才讓它在對的時間點紅。
> 前四版都是綠的，而且綠得很有自信 XD
```

## 交叉引用不要寫死日號

**不要像開天眼一樣，什麼都明確標註第幾天會講。** 具體來說，這些通通不要寫：

- 「Day14 會展開」「Day20 會直接對照兩種 JSON」→ 改成「後面會展開分享」
- 「接下來 Day3-13 整段治理基礎建設」→ 改成「在後面講到治理基礎建設時」
- 「接下來 27 天」「這 29 天」這種總天數
- 「剩下天數的地圖」那種把 DayNN 區間畫成方框的流程圖——整張不要畫。要畫因果鏈就只標階段名稱（治理 → Signal Plane → agent 決策），不標日號
- 「今天沒做的事」表格裡那一欄「什麼時候展開」——只寫「留給後面處理」

兩個理由。一是編號一直在動（v5 把 16 篇併成 12 篇），每次重編都要回頭掃全部文章的交叉引用，漏掉一個就是給讀者一個指到錯誤位置的指標。二是**寫的當下根本還不知道**——順序臨時會調整，先承諾了就等於欠一筆債。

例外只有一個：每篇開頭那句程式碼連結（「程式碼在範例 repo 的 `dayNN/`」），那是指向一個已經存在、不會再動的資料夾。

## 踩到的坑就是內容，不是雜訊

這系列最有價值的段落幾乎都來自「真的踩到」的東西——`-r .` 的假綠燈、policy 只比對名字前綴、`infer` 還原不出 `brief`。寫到這種東西時：

- 完整寫出「表面看起來沒事、實際上出了什麼問題」，附真實輸出當證據
- 把它連回這系列的主軸（治理 → 資料可信度 → agent 判斷），不要只當成工具 bug 記一筆
- **不要為了讓文章漂亮而修掉這些坑**。一個「檢查通過但其實是錯的」的案例，比三個都成功的案例有用

## AIOps 主軸要一路帶著

這不是一個純 Weaver 教學系列。每一天的治理動作，都要能回答「這對後面 agent 的判斷品質有什麼影響」。例如講 `enum` 的 `members` 時，要點出那是 LLM 唯一能事先知道 label 值域的來源；講 schema 一致性時，要連回 Day2 的「缺語意」。沒有這條線，文章會退化成工具手冊。

## 治理要用 platform engineering 的角度收

主軸是治理，但「治理」這個詞很容易寫成一種**由上而下的管制**——寫出來的文章會像在教一個中央團隊怎麼多設幾道關卡。這系列要刻意站在另一個位置：治理是**平台團隊提供給產品團隊的能力**，registry、CI gate、policy 都是內部平台的介面，而不是稽核清單。

每一天除了「這個機制怎麼運作」，還要能回答下面這幾個問題中的至少一個。不必每篇都全部答（也不要寫成問答式的條列），但一篇如果一個都答不出來，就代表它只寫了工具、沒寫工程：

- **誰維護、誰使用。** 這個 registry／policy／workflow 是平台團隊擁有的，還是每個產品團隊各自一份？改它需要誰同意？（Day8 的分層就是這個問題的機制化：哪一層統一、哪一層放手。）
- **產品團隊要付多少成本。** 一個新服務要接上這套治理，實際要做的事有幾件、要學幾個新概念？如果答案是「先讀完 registry 規格」，那這個設計就把成本推給了使用者。
- **失敗的時候，錯誤訊息夠不夠讓對方自己修好。** 這是治理能不能規模化的分水嶺：一道 gate 如果擋下來之後還要平台團隊親自去解釋，它的維護成本會隨團隊數線性成長。所以文章裡看到「訊息誤導」「annotation 落不到行上」「panic 沒有診斷」這類坑時，要明確寫出它的 platform 代價，不要只當成 UX 抱怨。
- **這條規則是強制、預設、還是建議。** 對應到三層驗證模型：hard error 是強制，`--future` 是平台團隊替所有人做的一個時程決定，Rego policy 是可以按團隊分級的。paved road 的重點從來不是「只有一條路」，是「預設那條路最好走，要走別條得自己說明理由」。
- **演進的責任在哪一邊。** base 改版時，是平台團隊負責通知並提供遷移期，還是產品團隊自己發現？（Day9 那個「deprecation 是宣告、不是通知」就是這個問題的具體形狀。）

語氣上要注意兩件事。一，**不要用「規範」「強制」當形容詞去描述整個系列的目標**——這系列真正主張的是「讓對的事情比錯的事情好做」。二，治理的成本要誠實寫，包含平台團隊自己的成本（多維護一份 policy、多釘一個版本、多一個要回答的問題），不要只寫產品團隊被擋下來的部分。

這個角度跟 AIOps 主軸是同一條因果鏈的兩端：**平台團隊把治理做成好用的介面 → 產品團隊真的照做 → 遙測資料一致可信 → agent 的判斷才有依據。** 中間任何一環是靠人盯著，這條鏈就斷了。所以「能不能自動化」跟「能不能被 agent 消費」在這系列裡是同一個標準的兩種說法。

## 對應的程式碼放另一個 repo

可執行的範例、policy、registry 放 `otel-aiops-agent/dayNN/`，文章只貼重點片段跟真實輸出，並在開頭連過去，該 repo 的 `dayNN/README.md` 寫完整重現步驟。

**文章裡不要出現「submodule」這個詞**——那是我這邊的工作方式，讀者只會看到 GitHub 上的一個 repo。開頭的連結一律寫成「程式碼在範例 repo [`OTel_AIOps_Agent`](網址) 的 [`dayNN/`](網址)」，指令的前提寫「從 repo 根目錄跑」。

**資料夾日號跟文章一致。** 文章 DayN 就對應 `dayNN/`：現在是 `day01`、`day03`–`day17`、`day21`–`day27`、`day29`–`day34`。純概念日沒有資料夾（`day02`、`day18`–`day20`、`day28`），那幾天開頭不用寫程式碼連結。也沒有 `testability/`，Day12 的東西在 `day12/`。

**改號的時候記得三個地方一起改**（v10 把 43 天壓成 40 天、v11 把 40 天壓成 34 天時各走過一次）：文章的 `title:`／`# ` 標題／內文的 repo 連結、`dayNN/README.md` 的第一行標題、以及腳本 docstring 裡那行執行指令的路徑。最後跑一次「檔名 vs 標題」「文章連到的資料夾存不存在」的對照，比人眼掃可靠。

**那個 repo 的佈局要寫對**（曾經寫錯過）：

- 那個 repo 裡**沒有** `demo-services/` 這個目錄。它存的是每一天當下那組 stack 的**完整快照**，一天一個資料夾：`dayNN/services/{api-gateway,order,payment,user,webapp}`、`dayNN/shared/`、`dayNN/k8s/`、`dayNN/weaver/`。
- `demo-services/` 是**主 repo** `o11y-bench/` 底下的目錄，是這組服務持續演進的地方。文章裡用 `demo-services` 稱呼這組服務沒問題（Day1 就是這樣介紹的），但**不要說它在範例 repo 裡**，也不要寫成那個 repo 的路徑。
- 文章裡的指令一律假設在範例 repo 的根目錄下跑，路徑從 `dayNN/` 開始寫（`-r day06/weaver/registry`），不要寫裸的 `weaver/registry`——那在根目錄下不存在。
- 貼路徑之前先 `ls` 確認一次。這類錯誤讀者一照做就會撞到。
