### 🕒 第 2 小時：將 Weaver 整合入 CI/CD 流程

#### ⚙️ 第一階段：GitHub Actions 整合與自動化工作流 (20 分鐘)

**【教學目標】學習如何使用官方 Action 將 Weaver 無縫嵌入 GitHub 的 Pull Request (PR) 檢查中。**

* **環境準備 (`setup-weaver`)：**
  講師介紹官方提供的 `setup-weaver` GitHub Action。這個 Action 可以在 CI/CD pipeline 中快速安裝並設定 Weaver 執行環境，完全不需要開發者手動下載二進位檔。
* **建立三大核心 CI 檢查任務 (CI Checks)：**
  參考官方 `opentelemetry-weaver-examples` 專案中的最佳實踐，講師帶領學員在 `.github/workflows` 目錄下建立三個關鍵的自動化工作流：
  1. **驗證模型與政策 (Validate Examples)：** 每次 PR 提交時，自動執行 `weaver registry check`，確保新增或修改的 YAML Schema 與 Rego 自訂策略沒有語法錯誤或違反向後相容性。
  2. **檢查生成的程式碼是否同步 (Check Generated Code)：** 確保開發者修改了 Schema 後，有記得重新生成 Go/Java 程式碼，防止「設計圖」與「程式碼 SDK」脫節。
  3. **檢查文件是否同步 (Check Documentation)：** 確保自動生成的 Markdown 規格文件與最新的 Schema 保持一致。

#### 📡 第二階段：在測試階段執行 Live-check 實作 (20 分鐘)

**【教學目標】將靜態檢查升級為動態驗證，利用整合測試攔截實際發送的錯誤遙測資料。**

* **架構設計與連線設定：**
  講師說明在 CI 執行整合測試 (Integration Test) 時，如何讓 Weaver 扮演一個 OTLP 接收端。

  * 我們可以配置測試中的應用程式（或 OTel Collector），將遙測訊號 (OTLP stream) 直接發送給正在運作的 `live-check` 實例。
* **執行 Live-check 指令：**
  講師示範在 CI 腳本中加入以下指令，啟動 Weaver 監聽服務：

  ```
  weaver registry live-check \
  --registry ./telemetry-schema \
  --policy ./policies \
  --input-source otlp \
  --format yaml \
  --output ./weaver-report.yaml \
  --otlp-grpc-address 0.0.0.0 \
  --otlp-grpc-port 4318
  ```

  *原理解析：* 這個指令會讓 Weaver 在 `0.0.0.0:4318` 啟動 gRPC 伺服器接收資料，並以 YAML 格式輸出最終的合規報告。程式在測試期間發出的所有 Metrics, Spans, Logs 都會被 Weaver 實時捕捉並與 Registry 進行比對。

#### 🛡️ 第三階段：打造把關機制與覆蓋率報告 (15 分鐘)

**【教學目標】演練破壞性測試，見證 Weaver 如何阻擋錯誤程式碼進入生產環境。**

* **實作演練：刻意植入錯誤**
  1. 講師請學員在應用程式碼中，刻意將一個已經在 Schema 規範好的指標屬性名稱打錯（例如把 `payment.order_id` 寫成 `order_id`）。
  2. 提交程式碼並觸發 GitHub Actions 執行整合測試。
* **見證把關機制 (Exit Code 1)：**
  * 測試執行時，Weaver 收到 `order_id`，立刻發現這與 YAML 規格書不符。
  * 當測試結束，Live-check 會在報告中標示出這項違規，並以  **退出代碼 1 (Exit Code 1) 終止程序** 。
  * **結果：** CI 流程亮起紅燈，PR 被阻擋合併，成功防止錯誤的遙測命名混進生產環境。
* **解讀合規與覆蓋率報告 (Coverage Report)：**
  講師打開剛才輸出的 `./weaver-report.yaml`，向學員展示裡面的各項統計數據。其中非常關鍵的一項是  **「覆蓋率 (Coverage)」** 。
  這能幫助團隊確認：*「我們寫的整合測試，到底有沒有觸發到 Registry 中定義的所有遙測訊號？」* 如果覆蓋率太低，代表有許多遙測指標根本沒被測試到，團隊就應該考慮補齊相關的測試案例。

#### 🙋 第四階段：隨堂交流與 QA (5 分鐘)

**【教學目標】解答 CI 整合痛點，並為下一階段的 AI 重構鋪路。**

* **討論：** 在現有專案導入 Live-check 會不會讓 CI 跑太久？如何只針對變更的微服務進行驗證？
* **總結與預告：**
  現在，只要開發者寫錯遙測程式碼，CI 就會無情地把它擋下來。但這也意味著開發者必須回頭去「重構」這些錯誤。下一個小時，我們將介紹如何啟動  **Weaver MCP 伺服器** ，召喚 AI 助理來自動幫我們修復這些過不了 CI 的程式碼！
