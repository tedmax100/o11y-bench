### 🕒 第 4 小時：靜態驗證與自訂策略 (Policy) 防護

#### 🛡️ 第一階段：靜態驗證與 Policy 概念引入 (10 分鐘)

**【教學目標】理解基礎 YAML 檢查與企業客製化規範（Policy）的差異。**

* **基礎靜態驗證回顧：**
  講師帶領學員回顧上一個小時使用的 `weaver registry check --registry <目錄>` 指令。這個指令能確保 YAML 格式正確、指標定義有包含單位等基礎語法與語義檢查。
* **為什麼我們需要自訂策略 (Policy)？**
  單純的 OpenTelemetry 規範無法滿足個別企業的特殊需求。例如：
  * 公司規定所有自訂指標都必須加上公司名稱的前綴（Prefix）。
  * 在官方標準中被列為「選填 (optional)」的欄位（例如 `brief` 描述欄位），在公司內部規定一律必須「必填」。
  * 驗證附加在屬性或遙測訊號上的特定註解 (annotations) 是否合乎規定。
* **技術核心：Open Policy Agent (OPA) 與 Rego：**
  Weaver 透過整合 Open Policy Agent (OPA)，支援使用 **Rego 語言**來撰寫這些自訂的政策型靜態驗證規則 (Policy-based static validation check)。

#### 📝 第二階段：撰寫第一條 Rego 防護策略 (15 分鐘)

**【教學目標】學習如何編寫 Rego 腳本，並與 Weaver 結合執行。**

* **情境設定：強制規範共用資源屬性 (Resource Attributes)**
  在微服務架構中，有些屬性是全域通用的，例如代表程式碼版本的 `git.tag` 或是部署環境。如果工程師忘記在配置中宣告這些欄位，日後排查問題將變得非常困難。
* **實作演練：**

  1. 講師指導學員建立一個 `policies/enforce_git_tag.rego` 檔案。
  2. 在檔案中撰寫 Rego 規則： **「所有服務上報的 Resource 數據中，必須強制包含 `git.tag`，否則一律視為不合規！」** 。
* **觸發 Policy Check：**
  學員在終端機中執行帶有 `--policy` 參數的檢查指令：

  ```
  weaver registry check \
  --registry ./telemetry-schema \
  --policy ./policies
  ```

  觀察當 YAML 定義檔漏掉 `git.tag` 時，Weaver 如何根據 Rego 規則，在終端機報出架構錯誤並終止流程。

#### 🚨 第三階段：破壞性變更 (Breaking Changes) 與警報防護 (20 分鐘)

**【教學目標】了解如何透過 Weaver 防止開發者隨意刪除關鍵欄位，保護生產環境的警報系統。**

* **痛點重現：**
  講師請學員打開剛才寫好的 `payment.yaml`，並**刻意刪除**一個已經標記為「必填 (Required)」的屬性（例如：`payment.order_id`）。
  * *情境說明：* 在真實世界中，這個屬性可能已經被 SRE 團隊拿去寫成 Prometheus 或 Datadog 的警報規則。如果開發者隨便刪掉它，生產環境的警報就會直接失效。
* **架構演進防禦：**
  再次執行 `weaver registry check`。此時 Weaver 會跳出  **「向後相容性錯誤 (backwards compatibility error)」** 。
  * *原理解析：* Weaver 內建了架構演進 (Schema Evolution) 的規則檢查。它會比對變更，告訴你「你不能改變必填屬性，因為這會破壞現有的警報規則」。
* **解決方案討論：廢棄 (Deprecation) 機制**
  如果真的需要改名怎麼辦？講師介紹如何使用 `deprecated` 標籤，而不是直接刪除欄位。將舊欄位標示廢棄，並引導系統過渡到新欄位，實現安全的架構演進。

#### 🙋 第四階段：隨堂測驗與 Q&A 交流 (15 分鐘)

**【教學目標】確保學員掌握 `--policy` 的應用，並能舉一反三。**

* **進階挑戰：**
  請學員嘗試寫一條簡單的 Rego 規則（講師可提供範本讓學員填空），要求某個特定的自訂指標名稱必須以 `company_name.` 開頭。
* **Q&A：**
  開放討論，例如：Rego 語言的學習曲線？如何在 CI/CD（例如 GitHub Actions）中妥善管理這些統一個 Policy 檔案？
* **總結：**
  現在，我們的遙測資料不只有了「規格書」，還有了「法律（Policy）」。這兩者結合，構成了阻止錯誤程式碼上線的第一道堅固防線。
