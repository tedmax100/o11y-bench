### 🕒 第三小時：建立團隊的第一個遙測 Schema (實作)

#### 📂 第一階段：專案結構規劃與最佳實踐 (10 分鐘)

**【教學目標】學習如何組織 Schema 檔案，避免未來難以維護的「義大利麵條式」定義。**

* **建立專屬資料夾：** 所有遙測的結構定義都應該集中管理。請學員在專案根目錄下建立一個專屬資料夾，例如命名為 `telemetry-schema/` 或是 `telemetry/registry`。雖然 Weaver 不強制規定 YAML 檔案的名稱，但賦予有意義的檔名是好習慣。
* **⚠️ 黃金守則：不要把所有東西塞在同一個檔案裡！**
  * **按訊號拆分：** 建議將追蹤 (Spans)、日誌 (Events) 和指標 (Metrics) 寫在不同的 YAML 檔案中。
  * **按服務拆分：** 如果應用程式有多個微服務，應根據微服務名稱進一步分類。
  * **獨立共用屬性：** 跨服務都會用到的屬性（如 `git.tag`、`service.name`），應該獨立抽成一個檔案（例如 `common.yaml`）以供其他檔案參照，避免重複撰寫與未來修改時的遺漏。

#### 🧩 第二階段：定義共用資源屬性 (Common Attributes) (15 分鐘)

**【教學目標】實作 `common.yaml`，學習屬性的參照 (Reference) 機制。**

* **什麼是資源屬性？** 這是用來描述程式碼版本、部署環境或硬體設備等全域通用的欄位。
* **實作演練：** 講師帶領學員建立 `telemetry-schema/common.yaml`。
  * 在檔案中定義例如 `git.tag`（版本號）或 `deployment.environment`（部署環境）等屬性。
  * 設定這些屬性的類型 (type)、文字描述 (brief) 以及穩定度級別 (stability level，例如標示為 `stable` 或 `development`)。
* **講解參照機制：** 說明未來在定義具體的微服務訊號時，如何透過 `ref` 關鍵字直接引用這些共用屬性，這不僅能確保命名一致，還能大幅減少重複代碼。

#### 🛒 第三階段：為「訂單支付」微服務定義核心訊號 (20 分鐘)

**【教學目標】為具體的商業邏輯定義 Span 與 Metric，掌握訊號定義的核心元素。**

* **情境設定：** 假設我們正在開發一個電子商務的「訂單支付 (Order Payment)」微服務。
* **實作 Span (追蹤)：**
  * 建立 `payment.yaml`。
  * 定義一個用來追蹤支付流程的 Span，命名為 `payment.process`。
  * 為這個 Span 加入專屬的屬性，例如 `payment.order_id`。
* **實作 Metric (指標)：**
  * 在同一個邏輯群組下，我們需要一個計算支付金額或次數的指標，例如 `payment.amount` 或是類似拍賣系統的 `auction.bid.count`。
  * **必填欄位解析：** 指導學員設定指標的名稱 (name)、儀表類型 (instrument，例如 `updowncounter` 增減計數器)、測量單位 (unit，例如 `[bids]` 或 `USD`)，以及該指標的簡短描述 (brief)。

#### 🛡️ 第四階段：靜態驗證 (Registry Check) 與錯誤排除 (15 分鐘)

**【教學目標】學會使用 Weaver CLI 驗證 YAML 語法，並體驗錯誤攔截機制。**

* **執行靜態檢查：** 學員完成 YAML 撰寫後，在終端機輸入以下指令進行語法與語義的驗證：
  ```
  weaver registry check --registry ./telemetry-schema
  ```
* **除錯演練 (刻意犯錯)：**
  * 講師請學員故意將指標 (Metric) 中的 `unit`（單位）欄位刪除，或是故意打錯儀表類型 (instrument)。
  * 再次執行檢查指令，觀察 Weaver 如何精準報錯，提示開發者哪一個檔案的哪一行不符合 OpenTelemetry 的語義慣例規範。
* **總結：** 這個驗證動作是「可觀測性即設計」的第一道防線，確保所有的遙測規格書在進入開發階段前，就已經是完美且標準化的。
