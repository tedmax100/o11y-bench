### 🕒 第 1 小時：動態實時驗證 (Live-checking) 原理

#### ⚖️ 第一階段：靜態 vs 動態驗證的極限與突破 (20 分鐘)

**【教學目標】讓學員深刻理解為什麼光有 YAML 規格書是不夠的，必須檢查「實際產生的訊號」。**

* **靜態檢查的極限：**
  講師回顧第一天的 `weaver registry check` 指令。這個指令雖然能確保 YAML 規格書寫得完美無缺、符合語義慣例與自訂策略，但它 **無法約束工程師寫出的程式碼** 。
  * *痛點舉例：* 假設規格書要求指標屬性必須叫 `payment.order_id`，但新進工程師在寫 Go 程式碼時，手滑寫成了 `attribute.Key("order_id")`（漏了前綴）。這時靜態檢查完全抓不到錯誤，因為「設計圖（YAML）」是正確的，錯的是「實際施工（程式碼）」。
* **動態驗證 (Live-checking) 的誕生：**
  為了解決這個問題，Weaver 引入了「動態實時檢查」機制。
  * *運作原理：* 在測試環境（例如整合測試）執行應用程式時，Weaver 會像一個 OTLP 接收端一樣，直接攔截並檢查程式 **實際發送出來的遙測資料** （OTLP 串流）。
  * *核心價值：* Weaver 會當場拿收集到的實際訊號與你定義的 Schema 進行比對，就像是一個「遙測資料的單元測試」，徹底防堵不合規的命名混入生產環境。

#### 🎛️ 第二階段：Live-check 彈性的輸入與輸出設定 (20 分鐘)

**【教學目標】認識 Live-check 的架構，學習如何針對不同的環境配置輸入與輸出。**

* **極度彈性的輸入源 (Input Sources)：**
  講師說明 `live-check` 被設計得非常靈活，能適應各種測試情境。它支援多種資料輸入來源與格式：
  * **檔案路徑 (File path) / 標準輸入 (stdin)：** 適合將過去收集到的遙測資料存成純文字或 JSON 格式，再餵給 Weaver 進行批次檢查。
  * **OTLP 串流：** 這是最常用的方式。Weaver 可以直接啟動一個 gRPC 伺服器（例如監聽 `0.0.0.0:4318`），讓 OTel Collector 或應用程式直接把資料打過來。
* **多樣化的輸出報告 (Output Formats)：**
  * 檢查完成後，Weaver 會產出一份詳細的報告，指出哪裡不合規，並支援輸出為 **YAML、JSON 或 JSONL** 格式，方便後續的 CI/CD 工具進行自動化解析。
  * *覆蓋率 (Coverage) 統計：* 報告中還會包含測試覆蓋率的數據，讓開發者知道整合測試是否有涵蓋到 Registry 中定義的所有遙測訊號。

#### 🚀 第三階段：模擬遙測發送 (`weaver registry emit`) (15 分鐘)

**【教學目標】學習在應用程式還沒寫好之前，如何利用 Schema 自動產生遙測資料。**

* **情境引入：**
  通常在開發流程中，SRE 或維運團隊希望先建立好 Grafana 儀表板，但應用程式還沒開發完，沒有真實數據可以看怎麼辦？
* **`registry emit` 指令實作：**
  講師展示 Weaver 的另一個強大指令：`weaver registry emit`。
  * *運作原理：* Weaver 會讀取你的 YAML 規格書，並利用你在規格書裡面寫好的「簡短描述、指標類型」以及「範例值 (Examples)」，自動生成 **假的（模擬的）OpenTelemetry 遙測物件串流** 。
  * *實機演練：* 講師在終端機執行指令，將這些模擬訊號發送到指定的 OTLP 接收端（例如一個本地的 Collector 搭配 Jaeger 或 Prometheus），讓學員親眼看到根據 Schema 自動長出來的漂亮圖表與追蹤軌跡。這對於早期設計儀表板或測試遙測管線非常有用。
