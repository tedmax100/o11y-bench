# OpenTelemetry Weaver — 部落格草稿

> 接續第一天開頭：問題說明 + Semantic Convention + Weaver 定位

---

## 實際操作：從零建立你的 Telemetry Registry

### Step 1：定義你的 Schema

Weaver 的核心是一個 YAML 格式的 **Telemetry Registry**，也就是你的監測資料的「合約」。以一個電商系統為例，我們可以把共用屬性和各服務的 Span 定義分開存放：

**`telemetry/registry/common.yaml`** — 跨服務共用屬性

```yaml
groups:
  - id: common.resource
    type: attribute_group
    brief: "跨服務通用的資源屬性"
    attributes:
      - id: deployment.environment
        type: string
        stability: stable
        brief: "服務部署環境"
        examples: ["production", "staging", "development"]
        requirement_level: required

      - id: service.team
        type: string
        stability: stable
        brief: "負責此服務的團隊名稱"
        examples: ["payments", "cart", "auth"]
        requirement_level: recommended
```

**`telemetry/registry/cart-spans.yaml`** — 購物車服務專屬的 Span 定義

```yaml
groups:
  - id: span.cart.add_item
    type: span
    span_kind: server
    stability: stable
    brief: "將商品加入購物車的 Span"
    attributes:
      - ref: deployment.environment   # 引用共用屬性，不重複定義

      - id: cart.session_id
        type: string
        stability: stable
        brief: "購物車 Session 識別碼"
        examples: ["sess-abc123"]
        requirement_level: required

      - id: cart.item_id
        type: string
        stability: stable
        brief: "加入購物車的商品 SKU"
        examples: ["SKU-001"]
        requirement_level: required
```

> 注意 `ref: deployment.environment` 的用法——這是 Weaver 的「引用機制」，讓你在不同服務的 Schema 中共用同一個屬性定義，改一個地方、全部生效。

---

### Step 2：靜態驗證（CI 的守門員）

定義完 Schema 之後，第一件事是確認它符合你的組織規範。Weaver 支援用 [OPA（Open Policy Agent）](https://www.openpolicyagent.org/) 的 Rego 語言來寫自訂的 Policy。

**`policies/enforce_naming.rego`** — 命名規範 Policy

```rego
package otel_weaver

allowed_metric_prefixes := ["payment.", "cart.", "auth.", "inventory."]

# 指標必須以允許的前綴開頭
deny[msg] if {
    group := input.groups[_]
    group.type == "metric"
    not starts_with_any(group.metric_name, allowed_metric_prefixes)
    msg := sprintf("指標 '%s' 不符合命名規範，必須以 %v 開頭",
                   [group.metric_name, allowed_metric_prefixes])
}

# 所有屬性必須有 brief 說明
deny[msg] if {
    group := input.groups[_]
    attr := group.attributes[_]
    not attr.ref
    trim_space(attr.brief) == ""
    msg := sprintf("屬性 '%s' 缺少 brief 說明", [attr.id])
}
```

然後執行驗證：

```bash
# 正常 registry → 通過
weaver registry check \
  --registry ./telemetry/registry \
  --policy ./policies
# ✓ No after_resolution policy violation

# 加入違規 Schema 後 → 失敗
weaver registry check \
  --registry ./telemetry/bad-registry \
  --policy ./policies
# Violation: metric_naming_prefix
#   指標 'orders.total' 不符合命名規範，
#   必須以 ["payment.", "cart.", "auth.", "inventory."] 其中之一開頭
```

如果有人新增了一個不符合命名規範的指標，CI 就會在這步失敗，問題永遠不會跑到 production。這就是**可觀測性左移**的具體體現。

### Step 3：自動產生程式碼

Schema 驗證通過了，接下來可以讓 Weaver 直接幫你生成各語言的常數定義，完全不用手寫：

```bash
weaver registry generate \
  --registry ./telemetry/registry \
  --templates ./templates \
  go ./generated_from_template
```

輸出的 **`generated/semconv/cart.go`** 長這樣：

```go
// Code generated by Weaver from telemetry/registry. DO NOT EDIT.

package semconv

import "go.opentelemetry.io/otel/attribute"

// CART_SESSION_ID is the key for attribute "cart.session_id".
// Brief: 購物車 Session 識別碼
// Type: string | Stability: stable
const CART_SESSION_ID = attribute.Key("cart.session_id")

// CART_ITEM_ID is the key for attribute "cart.item_id".
// Brief: 加入購物車的商品 SKU
// Type: string | Stability: stable
const CART_ITEM_ID = attribute.Key("cart.item_id")

// CART_ITEM_QUANTITY is the key for attribute "cart.item_quantity".
// Brief: 加入的商品數量
// Type: int | Stability: stable
const CART_ITEM_QUANTITY = attribute.Key("cart.item_quantity")
```

工程師在寫 instrumentation 時，直接引入這個 package 就好：

```go
span.SetAttributes(
    semconv.CART_SESSION_ID.String(sessionID),
    semconv.CART_ITEM_ID.String(itemSKU),
    semconv.CART_ITEM_QUANTITY.Int(qty),
)
```

**不再有人拼錯 attribute name**，因為根本不需要手動輸入字串。

### Step 4：Live-check — 執行期的第二道防線

靜態驗證和程式碼生成保護了大多數情況，但還有一個場景沒有覆蓋：**第三方函式庫或舊服務打出了不符合規範的 telemetry**。

Weaver 的 `live-check` 模式可以作為一個 OTLP proxy，在資料流向後端之前即時比對 Schema：

```bash
# Weaver 監聽 4317，驗證後轉發到真正的 Collector
weaver registry live-check \
  --registry ./telemetry/registry \
  --policy ./policies \
  --input-source otlp \
  --otlp-grpc-address 0.0.0.0 \
  --otlp-grpc-port 4317 \
  --output ./reports/weaver-report.yaml
```

任何違反 Schema 的 span 都會被記錄在報告裡，讓你知道哪個服務、哪個屬性不符合規範——在測試環境就能抓到，而不是在 on-call 的半夜。

---

這四個步驟構成了 Weaver 的核心工作流程：**定義 → 驗證 → 生成 → 監控**。
