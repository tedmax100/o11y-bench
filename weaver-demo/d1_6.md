### 🕒 第 6 小時：型別安全 (Type-safe) 的程式碼生成

#### 🛡️ 第一階段：為什麼需要型別安全？ (15 分鐘)

**【教學目標】理解手動埋點的風險，以及將遙測視為「強型別 API」的觀念轉換。**

* **手動埋點的痛點：**
  過去在程式碼中加入遙測訊號時，工程師通常是手動輸入字串（例如 `payment.amount`）。這種做法極度脆弱，只要「手抖打錯字」或「大小寫不一致」（例如打成 `pay.amount`），這筆遙測數據就會無法與儀表板對接，導致生產環境的監控直接失效。
* **概念轉換：像對待 gRPC 一樣對待遙測資料：**
  講師說明，就像我們會用 gRPC 自動生成 Client 和 Server 的 Stub 程式碼來確保通訊格式一致，我們也應該用 Weaver 自動生成專屬的  **型別安全客戶端 SDK (Type-safe client SDK)** 。
  這不僅能避免拼字錯誤，更能將可觀測性從「自由發揮的字串」提升為「具有嚴格編譯檢查的程式碼介面」。

#### 🐹 第二階段：程式碼生成實作 (以 Go 語言為例) (25 分鐘)

**【教學目標】透過 Weaver 將 YAML 規格書自動轉換為 Go 語言的常數與封裝介面。**

* **基礎生成：常數 (Constants)**
  * 講師展示 Weaver 最基本的程式碼生成應用：將 Schema 中的屬性名稱轉換為各語言的常數。
  * **實作演練：** 透過 `weaver registry generate` 指令搭配 Go 模板，自動產出一份包含所有屬性（如 `payment.order_id`）的 Go 常數檔，工程師日後只需引用這些常數，完全杜絕拼字錯誤。
* **進階生成：型別安全的封裝介面 (Type-safe Wrappers)**
  * **情境展示：** 假設我們在 YAML 中定義了一個「拍賣出價次數 (Auction Bid Count)」的指標。
  * **代碼生成解析：** Weaver 會自動生成一個 `observability` 套件 (Package)。在這個套件裡，它會提供一個類似 `NewAuctionBidCountCounter` 的建構函式，以及一個型別安全的介面。
  * **應用層調用：** 開發者在處理出價邏輯時，不再需要手動查閱文件來拼湊指標名稱與單位，只需要直接呼叫 `bid.Add()`，並傳入合規的參數即可。

#### 💻 第三階段：IDE 整合與極致的開發體驗 (15 分鐘)

**【教學目標】體驗自動生成程式碼如何大幅降低開發者的認知負擔。**

* **IDE 自動補齊 (Smart Completion)：**
  當我們將自動生成的函式庫匯入專案後，開發者只要在 IDE（如 VS Code 或 GoLand）中輸入 `HTTP`，IDE 就會自動列出所有與 HTTP 相關的指標和屬性，省去在文件與程式碼之間來回切換的時間。
* **文件即註解 (Hover Documentation)：**
  由於 Weaver 在生成程式碼時，會把 YAML 裡定義的 `brief`（簡短描述）直接轉換為程式碼的註解（Docstrings）。
  * **實機展示：** 講師可以示範在 IDE 中，將滑鼠游標停留在（Hover）剛剛生成的 `bid.Add()` 方法或屬性常數上，IDE 會直接彈出該遙測欄位的詳細說明與測量單位。

#### 🙋 第四階段：第一天總結與 Q&A 交流 (5 分鐘)

**【教學目標】統整今日所學，並為明日的 CI/CD 實戰鋪墊。**

* **今日回顧：**
  我們從一開始認識「可觀測性即設計」的概念，接著親手撰寫了 YAML 規格書、加上了 Rego 的政策防護，最後用 Jinja2 模板將它們變成了 Markdown 文件與 Go 語言的強型別程式碼。現在，我們的遙測資料已經具備了與公開 API 同等的嚴謹度。
